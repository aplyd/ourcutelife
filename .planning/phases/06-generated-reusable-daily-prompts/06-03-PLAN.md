# Phase 6 Slice 06-03 — No-Credential AI Generation and Safe Fallback Plan

**Goal:** Add a locally testable, privacy-safe daily-prompt generation boundary that can validate and persist reusable AI prompts when a provider is available, while preserving the approved seed inventory as the automatic fallback and making no provider call in this repository slice.

**Business outcome:** The prompt library can gain warm, varied questions without making the daily ritual depend on OpenAI availability, exposing either partner's private data, or allowing malformed/unsafe model output into lifecycle assignment.

## Existing boundaries to preserve

- `convex/chatActions.ts` already demonstrates a Node-only Vercel AI SDK action using typed `env` declarations, but it sends user-authored private Chat text and writes Chat messages. Daily-prompt generation must use a separate action and must not reuse that input or persistence path.
- `convex/convex.config.ts` already declares `OPENAI_API_KEY` and optional `OPENAI_MODEL`. This slice does not add, read, validate, or modify a real credential.
- `convex/dailyPromptLibrary.ts` owns six deterministic approved seed prompts and normalized fingerprints.
- `convex/dailyPromptLifecycles.ts` transactionally ensures seeds, selects only approved bounded inventory, excludes recent couple assignments where possible, and freezes the selected prompt on the lifecycle.
- `convex/schema.ts` already gives `dailyPrompts` source, safety status, model, generation-prompt version, generated timestamp, completion count, and exact-fingerprint/ranking indexes.
- `convex/dailyPromptAssignments.test.ts` already proves that approved AI-shaped rows can participate in bounded selection while pending, rejected, malformed, or duplicate rows fail closed.

## Architectural rule

Generation replenishes the global reusable inventory **before** lifecycle assignment; it never runs inline from a lifecycle mutation or user request.

The boundary is:

1. A dedicated internal Node action requests a small bounded batch from an injected provider adapter.
2. The action receives only a versioned global generation policy and reusable-library metadata explicitly allowed below.
3. A pure deterministic validator normalizes and classifies each candidate.
4. One internal mutation revalidates the candidate and transactionally inserts it or returns an exact existing fingerprint.
5. Lifecycle planning continues to select from approved persisted inventory. If generation is unavailable, invalid, rejected, duplicated, or ambiguous, existing approved prompts and the six seeds remain usable without changing lifecycle behavior.

A mutation must not call an action. This slice does not wire recurring generation or couple-day lifecycle creation to the provider action.

## Privacy-safe bounded inputs

Provider input may contain only:

- the versioned generation system/guidance text
- a fixed requested candidate count with a small hard maximum
- the fixed allowed principle/category vocabulary
- up to a small bounded set of normalized fingerprints or approved reusable prompt texts used only to discourage duplicates

Provider input must not contain:

- prompt answers or `promptResponses`
- Moments, Moment summaries, feelings, requests, or tags
- Chat messages or monthly reviews
- user IDs, couple IDs, device/token data, names, emails, anniversaries, timezone, or location
- lifecycle recipient order, answer-start state, notification state, or completion rows
- any per-couple history or personalized context

Generation remains global and non-personalized in this slice.

## Generation guidance contract

Create a versioned policy constant for warm daily questions that:

- asks exactly one concise, answerable, non-leading question per candidate
- encourages appreciation, curiosity, connection, repair, support, or shared meaning
- is inspired by evidence-based relationship principles without claiming Gottman affiliation or copying proprietary language
- avoids diagnosis, treatment, therapy claims, crisis counseling, manipulation, blame, ultimatums, surveillance, sexual coercion, shame, abuse mediation, or requests for secrets
- avoids assumptions about gender, marriage, monogamy, living arrangements, finances, children, sex, health, religion, or relationship stage
- avoids multi-part questions, instructions to confront a partner, and prompts that require disclosing trauma or highly sensitive personal data
- requests structured candidate fields: `text`, `principle`, and `category`

Keep the model-facing policy in one module with an explicit version such as `daily-prompt-generation-v1`. Do not silently edit the text under an existing version.

## Deterministic candidate validation

A pure validator must run before persistence and again inside the persistence mutation. It must either return one canonical candidate or a stable rejection code.

At minimum validate:

- exact object shape and string fields only
- trimmed, bounded UTF-8 text and metadata lengths
- exactly one question mark at the end and no newline/list/multiple-question format
- allowed principle/category vocabulary
- normalized fingerprint matches `normalizeDailyPromptText(text)` and is non-empty
- no URLs, contact details, prompt-injection/meta-model text, diagnosis/therapy/medical claims, affiliation claims, hateful/harassing language, explicit sexual content, coercion, threats, self-harm instructions, or requests for secrets/private records
- no copied seed fingerprint or existing fingerprint without converging to the existing row
- no provider-supplied provenance, safety status, timestamps, completion count, IDs, rank, or source; these are server-owned

Static validation is a product safety gate, not a claim that model output is universally safe. Anything uncertain fails closed and leaves fallback inventory unchanged.

## Persistence and provenance

Add a narrow internal mutation, separate from the Node action, that accepts one validated candidate plus server-owned provenance:

- `model`
- `generationPromptVersion`
- `generatedAt`

The mutation must:

1. Re-run deterministic validation.
2. Query `dailyPrompts.by_normalized_fingerprint` with `.take(2)`.
3. Fail closed if more than one row exists.
4. If one exact compatible row exists, return it without changing text, metadata, safety status, completion count, or timestamps.
5. If no row exists, insert `source: "ai"`, `safetyStatus: "approved"`, server-owned provenance, `completionCount: 0`, and server timestamps.
6. Never overwrite, upgrade, or repair an existing seed, pending, rejected, malformed, or provenance-conflicting row.

No answer, identity, couple, Moment, Chat, notification, or per-couple completion data enters `dailyPrompts`.

### Generation-attempt observability

Do not add an attempt table in this slice. The action should return a privacy-safe aggregate result containing only bounded counts and stable outcome codes such as `generated`, `deduplicated`, `rejected`, `provider_unavailable`, or `provider_error`.

A durable attempt/audit table is a later slice because its retention, retry identity, operator access, and cleanup policy require separate design. Never persist raw provider output or error text merely for observability.

## Provider adapter and fallback

Create a dedicated daily-prompt Node action; do not extend `chatActions.ts`.

The action implementation must support an injected provider function for tests. Production wiring may use the already-installed Vercel AI SDK and typed OpenAI environment declarations, but this slice's verification must inject deterministic results and must not call the real adapter.

Fallback rules:

- Missing/blank provider configuration returns `provider_unavailable`; it does not throw through lifecycle planning and does not insert a prompt.
- Provider timeout, exception, malformed structured output, too many candidates, or partial output returns only stable privacy-safe codes/counts; it does not persist raw output/error data.
- Each candidate is independent: one rejected or duplicate candidate cannot approve another candidate implicitly.
- Zero accepted candidates is a successful fallback outcome because approved persisted inventory and seeds remain available.
- Retries converge by normalized fingerprint and cannot reset completion rank or mutate an existing assignment.
- The provider action is internal only and has no public client-callable wrapper.
- No cron, scheduler, lifecycle mutation, client route, or automatic provider invocation is added in this slice.

## Additive schema decision

No schema change is required for this slice. The existing `dailyPrompts` fields and indexes hold approved generated prompt provenance and support exact deduplication plus bounded approved selection.

If implementation discovers that a schema change is necessary, stop and revise this plan before editing `convex/schema.ts`; do not opportunistically add generation-attempt state.

## Test-first implementation order

### RED 1 — Policy and privacy contract

Add pure tests proving:

- the policy has a stable non-empty version and the accepted warm/non-affiliated guidance
- provider request construction contains no answer, Moment, Chat, user, couple, device, lifecycle, or notification fields
- candidate count, duplicate-avoidance context, text, and metadata are hard-bounded
- valid candidates normalize deterministically
- malformed shape, unknown fields, blank/oversized text, multiple questions, missing terminal question mark, newlines/lists, unknown principle/category, URLs/contact details, model/meta instructions, affiliation/diagnosis/therapy claims, coercion, threats, explicit sexual content, and secret/private-record requests receive stable rejection codes
- provider-owned attempts to set source, safety, rank, IDs, timestamps, or provenance are rejected

### GREEN 1 — Pure generation policy

Implement only the provider-neutral types, versioned prompt builder, input bounds, deterministic parser, and validator. No Convex action, mutation, env access, or network path yet.

### RED 2 — Transactional deduplication and provenance

Add `convex-test` coverage proving:

- one valid candidate inserts one approved AI prompt with server-owned model/version/time and zero completions
- replay of the same normalized fingerprint returns the exact row and leaves all fields unchanged
- punctuation/case/spacing equivalents converge by fingerprint
- duplicate fingerprint rows fail closed
- a conflict with seed, pending, rejected, malformed, or incompatible existing metadata cannot be overwritten
- caller-supplied source/status/count/timestamps/IDs cannot enter the mutation contract
- no private/user/couple/answer/Moment/Chat/notification fields appear on the stored row
- the new approved row participates in existing bounded selection, while assignment immutability and recent exclusion remain green

### GREEN 2 — Internal persistence boundary

Implement the internal mutation with validators, bounded indexed fingerprint lookup, pure revalidation, immutable convergence, and server-owned provenance.

### RED 3 — Mocked provider orchestration and fallback

Add action/orchestration tests with an injected provider proving:

- missing configuration returns `provider_unavailable` with zero writes and zero provider calls
- a valid bounded mocked response persists accepted candidates through the internal mutation
- mixed valid, rejected, and duplicate candidates produce only aggregate stable outcomes
- timeout, throw, malformed result, too many results, and empty result preserve fallback inventory and expose no raw provider output/error
- retrying the same mocked batch creates no duplicate and changes no completion count
- arguments and return values contain no private data
- the real Vercel/OpenAI adapter is not invoked by any test

### GREEN 3 — Internal action boundary

Implement the dedicated internal action and injectable adapter. Keep real invocation unreachable from cron, lifecycle planning, and clients in this slice.
