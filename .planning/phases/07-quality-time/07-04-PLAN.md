## Outcome

Add exactly one responder-side mobile slice on top of the approved Slice 07-02 server contract. A responder who already has a sent request ID can choose a non-empty subset of the requested categories, privately pass or accept only the initiator's shortlisted cards, stop each chosen category after its first mutual match, and see one completed combined result containing mutual options only. Both participants can open the same completed outcome projection.

This slice does **not** add request discovery, inbox/history, notifications, rescheduling, inventory generation, legacy cutover, backend behavior, deployment, migration, or live-data verification. The responder entry is exercised by exact fixture request route/deep link; how a real responder discovers that ID is a later plan.

The existing public API is authoritative:

- `qualityTime:getRequest({ requestId })`:
  - `sent`: neutral timing, requested categories, status, and version;
  - responder `responding`: own `responderCategories` plus `categoryResults`, where each category is either `pending` with remaining neutral `{ optionId, ...allowlisted card }` snapshots or `matched` with one neutral option;
  - initiator `responding`: neutral base only;
  - `completed`: both participants receive only selected-category `matched` option or neutral `no_match` results;
  - `canceled`/`expired`: neutral base only.
- `qualityTime:beginResponse({ requestId, expectedVersion, categories })`: responder-only, sent-only, one immutable non-empty unique subset of requested categories.
- `qualityTime:recordDecision({ requestId, expectedVersion, optionId, decision })`: responder uses **only** `optionId`; `planIdeaId`, category, user/couple/role, and authorship are never sent. A mutual accept creates one outcome transactionally and stops that category. A pass remains private. Completion occurs only after every responder-selected category is matched or exhausted.
- `qualityTime:cancelRequest({ requestId, expectedVersion })`: either participant may cancel `sent`/`responding`; terminal and stale writes fail closed.

Do not invent a separate responder inventory query, local matching algorithm, outcome mutation, empty category selection, editable category selection, or client-authored completion state.

## Privacy boundary

The mobile implementation must preserve all of these invariants:

1. No draft is discoverable or readable by the responder; this slice begins from an already `sent` fixture request ID.
2. Category selection is responder-private. The initiator waiting projection/UI must never expose selected/unselected categories, per-category progress, passes, accepts, order, exhaustion, or no-match reason.
3. Responder cards come only from `getRequest.categoryResults[].options`. Never query legacy inventory or display/transmit `planIdeaId`, initiator decision, source provenance, creator name, user/couple ID, timestamps, rejected IDs, or hidden-category cards.
4. Card copy must not say or imply “your partner liked/chose this.” Neutral copy may say only that the option is available for this request.
5. A responder pass and every non-matching accept remain private. No optimistic local match and no client-side comparison against an initiator list is allowed.
6. A category stops when the server projection changes it to `matched`; no remaining options or decisions for that category are rendered.
7. The combined outcome is rendered only from a `completed` projection. It contains the allowlisted card for each `matched` category and only a neutral category-level `no_match` for exhaustion. It omits responder-unselected request categories entirely because the completed server projection does.
8. Authorship remains hidden even after mutual match. The outcome says `You both want…`, never who suggested or accepted first.
9. Canceled, expired, malformed/not-found, and stale states reveal no cached cards or prior decision evidence. Clear/hide card content as soon as the authoritative projection is terminal or unavailable.
10. All mutation gates use the latest projected `version`; a stale response latches every responder write until a strictly newer projection arrives.

## Deterministic two-partner mock strategy

Extend the isolated fixture to model exactly two stable actors, `initiator` and `responder`, for one request. Role is selected only by a development/mock test harness and is never accepted by a production API argument.

- Keep stable request, option, actor, card, category, and ordering identifiers.
- Seed one sent request with requested categories `eat` and `entertainment`, three initiator-accepted options in each, and no responder decision.
- Fix outcomes deterministically:
  - Eat: responder passes the first card and accepts the second card, which is mutual and resolves Eat.
  - Entertainment: responder passes all three cards, producing `no_match` only when the request completes.
- Add a second resettable all-match scenario only if needed to prove natural-language joining across two mutual options; no random data or wall clock may affect it.
- The mock must derive projections by active actor: initiator sees only neutral waiting while responder chooses/swipes; responder sees only selected-category remaining options; both see the same completed allowlisted results.
- `beginResponse` validates exact responder role, sent status, unique non-empty subset, and version; writes once and increments once.
- Responder `recordDecision` accepts exact `optionId` only, validates shortlist membership/current category/version, records privately, increments once, creates at most one category outcome on deterministic mutual accept, stops matched categories, and completes only after all selected categories resolve.
- `cancelRequest` supports responder cancellation while sent/responding and returns only neutral terminal state.
- Add deterministic reset/scenario/actor controls through `globalThis.__OUR_CUTE_LIFE_QUALITY_TIME_MOCK__`, installed **only** when `isDevMockAuthEnabled` is true. It exposes exactly fixed enum operations `reset()`, `seed("mixed" | "all_match" | "all_no_match" | "expired" | "canceled" | "stale")`, `setActor("initiator" | "responder")`, and `advanceStaleProjection()`; it exposes no arbitrary state injection, decision inspection, identities, or production UI role switcher. The Argent debugger uses this bridge to alternate actors without reinstalling or manufacturing live users.
- Every successful mock operation notifies existing `useSyncExternalStore` listeners. Every stale, duplicate, wrong-actor, wrong-option, hidden-category, post-match, terminal, or malformed operation writes nothing.
- Unit tests inspect exact public keys and prove no actor IDs, authorship, initiator decision values, responder private decision values/order, rejected IDs, or hidden categories escape.

## Route and UI contract

### `/plans/quality-time/[requestId]/respond`

For `sent`:

- Show timing and only the locked requested categories.
- Expose each as a named toggle button: `Choose Eat for this Quality Time`, etc., with native `selected` state.
- Require at least one category and expose `Start choosing together` as a button with exact disabled/busy state.
- Call only `beginResponse` with `requestId`, current `expectedVersion`, and selected category values.
- Category choices cannot be edited after the mutation succeeds.

For responder `responding`:

- Show named selected-category navigation controls with selected state and neutral resolved/pending copy.
- Choose the first unresolved category in persisted responder order; after a category becomes matched or exhausted, move to the next unresolved category deterministically.
- Render one server-projected remaining option at a time.
- Expose `Pass {title}` and `Accept {title}` as buttons sharing exact disabled/busy state.
- Submit only `optionId`, current version, and `pass`/`accept`.
- Do not claim a save/match until a refreshed projection confirms it.
- If a `pending` category returns zero remaining options while another category remains, show neutral exhausted copy (`No shared option in {category} this time`) and continue; never reconstruct which decisions caused it.
- If a category is server-projected `matched` before overall completion, show only `Shared option found — moving on`, not its card/title; the combined cards wait for `completed`.
- Expose `Cancel Quality Time request` with existing native confirmation, disabled/busy/stale gates, and exact `cancelRequest` call. Argent may open and dismiss the sheet but must not confirm during the primary mutual-outcome walkthrough.

On `completed`, replace/navigate to `/plans/quality-time/[requestId]/outcome`. On `canceled` or `expired`, clear interactive content, show neutral copy and `Back to Plans`. On not-found/malformed projection, show an honest non-specific unavailable state without cached content.

### `/plans/quality-time/[requestId]/outcome`

- Query `getRequest` independently; do not pass cards/results through route params or local state.
- Render combined content only when status is `completed`.
- Heading: `Your Quality Time is ready`.
- Build one deterministic accessible summary from matched results only, for example `You both want to eat at Pasta night.` With multiple matches, join phrases in the server-projected category order.
- Render each mutual card with neutral allowlisted fields. Give each result an accessible label such as `Mutual Eat option, Pasta night`.
- Render a neutral `No shared Entertainment option this time` row for `no_match`, with no card, count, rejected ID, actor, or explanation.
- If every chosen category is `no_match`, show `No shared option this time` plus low-pressure restart copy; do not say who passed or suggest changing an answer.
- For `sent`/`responding`, show `Quality Time is still in progress` and link to the role-appropriate request/respond route without rendering results.
- For `canceled`/`expired`, show neutral terminal copy and `Back to Plans`; do not recreate/reschedule.
- The existing initiator request route may replace its completed placeholder with a named `View Quality Time outcome` button to this route. It must remain neutral while status is `sent`/`responding`.

## Required terminal/error behavior

- **Stale:** identify only the approved stale-version error shape, latch the submitted version, disable begin/decision/cancel writes through same-version rerenders, show `This request changed. Waiting for the latest state.`, and clear only after a strictly newer projection. Never auto-retry a decision.
- **Exhausted category while responding:** zero server-projected remaining options is neutral exhaustion for that responder-selected category; advance without showing decision history. Do not synthesize `no_match` into the combined outcome before completed.
- **Expired:** render only neutral expiry copy and navigation. A mutation returning `expired` is terminal, not a retry failure.
- **Canceled:** render only neutral cancellation copy and navigation; no actor/reason attribution.
- **No match:** consume only completed `categoryResults[].status === "no_match"`; show no option/private evidence. Mixed matched/no-match results are allowed.
- **Unavailable/malformed:** fail closed to a generic unavailable screen, clear cards, and perform no mutation. Do not reinterpret unknown statuses or missing result fields.
