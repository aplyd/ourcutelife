# Phase 6 Slice 06-05 — Reusable Prompt Inventory Replenishment Readiness Plan

Date: 2026-08-01

## Goal

Add one provider-free, privacy-safe readiness boundary that can decide whether the approved global prompt inventory needs replenishment and can supply bounded duplicate-avoidance context to the existing internal generation action. Do not schedule or invoke the model in this slice.

## Business outcome

The generated-prompt feature becomes ready for a later controlled replenishment trigger without wasting model calls on a healthy library or repeatedly asking for prompts the library already contains. Daily prompts remain available from the approved reusable inventory and six automatic seed fallbacks even when generation is unavailable.

## Protected baseline

- Preserve immutable couple-day assignment, canonical prompt reads/writes, private-until-both-submit answers, and exact-once aggregate completion counting.
- Preserve the approved-only 64-candidate ranking boundary, 12-assignment recency window, deterministic diversity policy, and exact selected-fingerprint verification from Slice 06-04.
- Preserve Phase 5 planner, scheduler, notification reservation/dispatch/outcome behavior, and the retired legacy fixed-hour cron.
- Preserve Slice 06-03's internal-only generation action, deterministic validator, server-owned provenance, exact-fingerprint convergence, and six-seed fallback.
- Do not change schema, mobile routes, prompt copy, notification code, cron wiring, credentials, provider configuration, billing, live data, or Phase 7.

## Confirmed gap

The generation policy can accept up to 12 existing approved prompt texts and converts them to normalized duplicate-avoidance fingerprints, but `generateReusableDailyPrompts` currently calls the orchestration boundary without any inventory snapshot. The action also has no provider-free decision boundary for distinguishing a healthy approved library from one that needs replenishment. The action remains intentionally unreachable from cron, lifecycle planning, and clients.

## Bounded readiness policy

1. Read approved reusable prompts only through the existing `dailyPrompts.by_safety_status_and_completion_count_and_created_at` index.
2. Read no more than the existing approved selection window of 64 rows.
3. Revalidate every row with the existing reusable-prompt document validator; malformed or duplicate IDs/fingerprints fail closed.
4. Count only valid approved rows. Do not count pending, rejected, malformed, or duplicate rows as available inventory.
5. Keep the six server-owned seed prompts as fallback inventory, but distinguish seed and AI rows in the aggregate readiness result.
6. Return only a bounded privacy-safe snapshot: stable readiness disposition, approved/seed/AI counts, and at most 12 approved normalized fingerprints for duplicate avoidance.
7. Make the replenishment threshold an explicit versioned constant. Initial implementation should target a small healthy floor that remains below the 64-row selection window and should request no more than the existing five-candidate generation maximum.
8. If evidence is malformed, duplicated, oversized, or ambiguous, return a fail-closed disposition that authorizes no provider call.
9. When the library is healthy, authorize no provider call.
10. When the library is below the explicit floor, compute only the bounded candidate count needed to move toward that floor.

The readiness boundary receives no prompt answers, response rows, completion rows, user or couple identity, assignment history, Moments, Chat, device/token data, notification state, timezone, or location. Aggregate `completionCount` is not needed for replenishment readiness and should not cross this boundary.

## Architectural boundary

- Add a pure provider-neutral inventory-readiness helper with strict input/output bounds.
- Add one internal query that reads and revalidates the bounded approved inventory and returns the privacy-safe readiness snapshot.
- Let the existing internal Node generation action call that internal query before provider orchestration.
- If readiness is `healthy` or fail-closed, return an aggregate no-generation result without constructing or invoking the provider.
- If readiness is `replenish`, pass only the approved bounded duplicate fingerprints and computed candidate count into the existing orchestration boundary.
- Keep the action internal and unreachable from public clients, lifecycle mutations, scheduler jobs, and cron in this slice.

Because Convex actions cannot read `ctx.db`, the inventory read must remain a separate internal query invoked through `ctx.runQuery`. The query needs complete argument and return validators. Use typed generated function references or a narrowly typed `makeFunctionReference` consistent with the current generated-code boundary.

## Test-first order

### RED 1 — Pure readiness policy

Capture missing-boundary failures for:

- empty, seed-only, below-floor, exactly-at-floor, and above-floor inventories
- candidate count capped by the existing five-candidate maximum
- deterministic 12-fingerprint duplicate context
- duplicate IDs and normalized fingerprints
- malformed status/source/fingerprint evidence
- unsafe counts, oversized input, and ambiguous evidence
- proof that healthy and fail-closed dispositions authorize zero requested candidates
- exact output shape containing no private or per-couple fields

### GREEN 1 — Pure readiness boundary

Implement only the constants, types, validator, and deterministic decision helper. No Convex function, provider adapter, environment access, scheduler, or network path.

### RED 2 — Bounded approved-inventory query

Add `convex-test` coverage proving:

- only approved rows from the existing bounded index enter the snapshot
- pending/rejected rows do not count
- seed and AI counts remain aggregate-only
- duplicate or malformed approved rows fail closed
- reads remain bounded at 64
- returned duplicate context is capped at 12 and deterministic
- no answer, user, couple, lifecycle, Moment, Chat, device, or notification table is read

### GREEN 2 — Internal query

Implement the internal query with validators, the existing approved index, `.take(64)`, document revalidation, and the pure readiness helper. Do not alter schema or persisted rows.

### RED 3 — Internal action preflight

Add injected-provider/action-orchestration tests proving:

- healthy inventory makes zero provider and persistence calls
- fail-closed inventory makes zero provider and persistence calls
- below-floor inventory requests only the computed bounded count
- duplicate-avoidance context reaches the provider as fingerprints only
- missing provider configuration still makes zero provider/persistence calls
- provider errors and rejected batches preserve the seed/approved fallback
- no real adapter or network call occurs in tests
- source search still finds no public, client, lifecycle, scheduler, or cron invocation path

### GREEN 3 — Readiness-aware internal action

Have the existing action call the internal readiness query and pass its bounded result to the existing orchestration. Preserve all current aggregate outcome codes unless a new stable `inventory_healthy` or `inventory_invalid` outcome is necessary; if the return contract changes, keep it aggregate-only and update direct tests before implementation.

## Argent applicability

Argent is not applicable. This slice changes only a pure inventory-readiness helper, one internal Convex query, internal generation-action preflight, and backend tests. It changes no client route, rendered content, accessibility contract, interaction, notification delivery, or mobile runtime behavior. If implementation unexpectedly touches a mobile surface, stop and revise the plan before continuing.

## Explicit non-goals

- No cron, scheduler job, recurring generation, lifecycle-triggered generation, or client-callable generation.
- No real provider/model call, credential access/change, environment change, billing decision, or live configuration.
- No schema, generation-attempt/audit table, retry queue, operator console, or alerting.
- No answer-, Moment-, Chat-, identity-, location-, or couple-derived generation or ranking input.
- No semantic similarity, embedding, rating, editorial moderation, or answer-derived quality score.
- No change to selection ranking, prompt assignment, response privacy, completion counting, notifications, or Quality Time.
- No migration, deployment, live data operation, push, or external communication.

## Definition of done

This slice is done only when a bounded indexed inventory snapshot deterministically authorizes either no provider call or a small replenishment request; healthy, malformed, duplicate, oversized, unavailable, and ambiguous states make zero provider calls; the existing generation action receives only approved global duplicate fingerprints and remains internal and unscheduled; seed fallback, approved-only assignment, ranking, privacy, and Phase 5 notification behavior remain green; independent review has no unresolved Medium-or-higher findings; and no provider, credential, deployment, migration, live-data, notification, or mobile action occurs.
