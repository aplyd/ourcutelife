# Phase 5 Daily Prompt Notification Lifecycle — Executable Plan

**Goal:** Implement REQ-PROMPT-001 through REQ-PROMPT-005 without changing Phase 6 prompt-generation scope or weakening private-until-both-submit behavior.

**Architecture:** A persisted couple-day state machine is the source of truth. Device permission/token rows determine readiness and routing; a canonical couple timezone determines prompt dates and the first delivery timestamp; authenticated answer-start events schedule the second step. Provider dispatch is isolated behind reserved idempotent attempts.

**Tech stack:** Expo SDK 56, Expo Notifications, Expo Router, Convex 1.41, TypeScript, Node test runner for pure helpers, `convex-test` + Vitest + edge runtime for backend functions, Argent for mobile verification.

## Proposed data model

### Modify `convex/schema.ts`

1. Add optional `promptTimezone` and `promptTimezoneUpdatedAt` to `couples` for additive compatibility.
2. Replace/extend token operational fields with a dedicated `notificationDevices` table:
   - `coupleId`, `userId`, `deviceId`, optional `pushToken`, `platform`
   - `permissionStatus`: `undetermined | denied | granted | revoked`
   - optional valid `timezone`, `enabled`, `lastObservedAt`, `createdAt`, `updatedAt`
   - indexes `by_user_and_device_id`, `by_couple_id_and_user_id`, `by_push_token`, `by_enabled_and_updated_at`
3. Add `dailyPromptLifecycles`:
   - `coupleId`, `promptDate`, `timezone`
   - `firstUserId`, `secondUserId`, `randomizedFirstLocalMinute`, `firstScheduledAt`
   - first/second step status unions, optional start/scheduled/sent/skipped timestamps and reason
   - `createdAt`, `updatedAt`
   - indexes `by_couple_id_and_prompt_date`, `by_first_scheduled_at_and_first_status`, `by_second_scheduled_at_and_second_status`
4. Add `dailyPromptDeliveryAttempts`:
   - `lifecycleId`, `coupleId`, `promptDate`, `step`, `recipientUserId`, `idempotencyKey`
   - `deviceId`, optional token reference/hash, `status: reserved | provider_accepted | provider_rejected | sending_unknown`
   - minimal optional Expo ticket ID/error code, timestamps
   - indexes `by_idempotency_key`, `by_lifecycle_id_and_step`, `by_status_and_created_at`
5. Add `startedAt` to `promptResponses` only if start and answer remain one row; preferred bounded design is a separate `dailyPromptAnswerStarts` row keyed by `coupleId`, `promptDate`, `userId`, with indexes `by_couple_id_and_prompt_date` and `by_user_id_and_prompt_date`.

Do not delete `pushTokens` or `lastPromptReminderDate` in the additive Phase 5 migration. Stop using the legacy path only after new tests pass; cleanup is a later approved migration.

## State invariants

- Unique logical lifecycle: one row for `(coupleId, promptDate)`; every creation mutation queries with that compound index and returns the existing row on replay.
- Frozen schedule: timezone, recipient order, random minute, and first timestamp never change after `first_scheduled`.
- Alternation is based on the preceding persisted lifecycle's `firstUserId`.
- First and second attempt keys are `${lifecycleId}:first` and `${lifecycleId}:second`; one attempt row per key.
- A due send revalidates membership, permission, and eligible routing token before reservation.
- `started answering` is accepted once per `(coupleId, promptDate, userId)` and server timestamp; duplicate calls return the original result.
- Only the assigned first user's start schedules the second step. The second user's independent start is recorded but never schedules a notification back to the first.
- The second timestamp is exactly `firstStartedAt + 300_000` and is persisted once.
- Sent/accepted/terminal steps are monotonic and never retried.
- An ambiguous reserved send is not automatically redispatched.

### Slice 05-04 — Couple-day planner and first delivery

**Create:**

- `convex/dailyPromptScheduler.ts`
- `convex/dailyPromptDispatch.ts`
- corresponding Convex tests

**Modify:**

- `convex/crons.ts`
- `convex/push.ts` to retire the legacy reminder from cron without deleting historical fields/functions yet

Behavior:

- A bounded internal planner scans eligible couples with cursor/batch continuation, derives the next couple-local date, and transactionally creates-or-returns one lifecycle.
- Persist timezone snapshot, ordered recipients, random minute, and `firstScheduledAt` once.
- Use `ctx.scheduler.runAt(firstScheduledAt, internal.dailyPromptDispatch.sendFirst, { lifecycleId })` after creation; duplicate planner runs must not schedule a second logical attempt.
- `sendFirst` revalidates lifecycle step, membership, permission, and most-recent eligible device.
- Reserve `${lifecycleId}:first` before calling Expo. On `ok`, persist minimal ticket metadata and mark first accepted. On deterministic rejection, mark rejected/skip and disable `DeviceNotRegistered`. On thrown/ambiguous post-dispatch failure, retain no-resend ambiguity state.
- Provider payload: generic title/body and route data only; include `promptDate` as non-sensitive routing context if the route can consume it safely.

Tests: duplicate cron/planner, alternating days, persisted random minute, timezone snapshot, token rotation after scheduling, revoke before due, multiple devices chooses latest, provider accepted/rejected/ambiguous, and >100-row batching without starvation.

## Privacy and security acceptance checks

- Public mutations derive authenticated identity server-side and confirm current couple membership.
- No query returns partner permission/device/token details to the other partner beyond a coarse couple readiness state.
- Never log or persist full answer text in dispatch/lifecycle/attempt records.
- Never include answer text, prompt text, moments, tags, therapy claims, or partner-specific progress in a push body.
- Keep raw Expo tokens only in routing tables; attempt history stores a token/device reference or one-way hash, not redundant raw tokens.
- Preserve existing `partnerResponse` reveal only when both responses exist.
- Retain lifecycle/attempt history on revoke/timezone change for auditability; do not expose it cross-couple.

## Definition of done

Phase 5 implementation is done only when every accepted requirement has deterministic test evidence; one lifecycle exists per couple-day; first recipient/time/timezone are frozen; duplicate calls cannot create another logical dispatch; second scheduling is tied to the first non-empty answer start; privacy checks pass; Argent evidence or a precise platform blocker is recorded; and no deploy/migration/push occurred without separate approval.
