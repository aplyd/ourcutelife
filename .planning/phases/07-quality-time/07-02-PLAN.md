## Additive data contract

All category validators use only `eat`, `drink`, `explore_adventure`, `entertainment`, and `romance`. Category arrays are validated as unique and bounded to 1–5 entries before persistence. Timestamp/version fields are server-owned finite values. Persist no client-authored user, role, couple, authorship, status, version, or outcome identity.

### `qualityTimeRequests`

Fields:

- `coupleId`, `initiatorUserId`, `responderUserId`.
- `timingKind: "now" | "future"` and optional `scheduledFor`; `now` forbids `scheduledFor`, while `future` requires a finite timestamp strictly in the future at creation.
- `selectedCategories`: immutable 1–5 unique category snapshot.
- optional `responderCategories`: immutable non-empty unique subset selected by the responder after send.
- `status: "draft" | "sent" | "responding" | "completed" | "canceled" | "expired"`.
- monotonically increasing integer `version` starting at 1.
- `createdAt`, `updatedAt`, and optional `sentAt`, `completedAt`, `canceledAt`, `expiresAt`.

Indexes:

- `by_couple_id_and_updated_at` on `coupleId`, `updatedAt` for a later bounded inbox/history query.
- `by_couple_id_and_status_and_updated_at` on `coupleId`, `status`, `updatedAt`.

No list query is required in this slice; these indexes prevent a future scan without expanding this API scope.

### `qualityTimeOptions`

One immutable request/category/card snapshot per considered initiator card:

- `requestId`, `coupleId`, `category`, `planIdeaId`.
- neutral immutable display fields copied from the authoritative idea: `title`, `description`, normalized `kind`, `costLevel`, `durationMinutes`, bounded `vibeTags`, and optional `photoUrl`/`address`.
- optional `sourceCreatedByUserId` as **server-private provenance only**; no public projection may spread or return the document.
- `createdAt`.

Indexes:

- `by_request_id_and_category_and_created_at`.
- `by_request_id_and_plan_idea_id`.

Use `.take(2)` on the second index and fail closed if duplicate option rows exist. Snapshot only an idea from the request's exact couple whose legacy category maps exactly through 07-01 policy; unknown historical categories fail closed rather than being rewritten.

### `qualityTimeDecisions`

One immutable private decision per request/option/actor:

- `requestId`, `coupleId`, `optionId`, `category`, `userId`, `decision: "accept" | "pass"`, `createdAt`.

Indexes:

- `by_request_id_and_user_id_and_category_and_created_at`.
- `by_request_id_and_option_id_and_user_id`.
- `by_option_id` for bounded fail-closed detection of any extra actor/request/category decision attached to an option.

The initiator may decide on at most 64 unique cards per selected category, including passes; the responder can see and decide only the 3–5 accepted shortlist options in each responder-selected category. Every read uses an index plus one overflow sentinel (`take(limit + 1)`), and overflow is invalid rather than truncated into apparently valid state. Each current-category option must have exactly one attached initiator decision; an option-first `.take(2)` rejects compensated extra actor, request, category, or couple evidence. Duplicate/ambiguous decision rows fail closed.

### `qualityTimeOutcomes`

At most one mutual outcome per request/responder-selected category:

- `requestId`, `coupleId`, `category`, `optionId`, `matchedAt`, `createdAt`.

Indexes:

- `by_request_id_and_category`.
- `by_request_id_and_created_at`.

Read each category with `.take(2)` and all request outcomes with `.take(6)`; duplicates or impossible category/option links fail closed. Outcomes contain no decision order, rejected IDs, actor IDs, or authorship.

## Authentication, membership, and role contract

Every public function has exact argument validators and derives the viewer with the repository's authenticated-user boundary, preferring canonical Better Auth and retaining only the established `ctx.auth.getUserIdentity().tokenIdentifier` test fallback if required by `convex-test`.

For every query and mutation:

1. Load membership by `by_user` with `.take(2)`; zero means unpaired and two means ambiguous, both fail closed.
2. Load the couple's members by `by_couple` with `.take(3)` and require exactly two distinct member rows/users.
3. For an existing request, require the current couple and exact two users to match its persisted initiator/responder snapshot. Changed, duplicate, missing, cross-couple, or ambiguous membership fails closed.
4. Derive `initiator` or `responder` by comparing the authenticated user to that snapshot. Never accept `userId`, `coupleId`, `initiatorUserId`, `responderUserId`, role, or creator identity as an API argument.

## Exact public API

Keep all functions in `convex/qualityTime.ts`. Return explicit allowlisted projections; never return/spread raw request, option, decision, plan idea, membership, user, or outcome documents.

### `createDraft` mutation

Arguments: timing discriminated union and `selectedCategories` only.

- Validate the exact pair and categories, derive initiator/responder server-side, and insert one draft at version 1.
- Compute a bounded server-owned expiry value; policy may be a fixed documented duration, but callers cannot supply it.
- Return only `requestId`, `status: "draft"`, and `version`.
- No partner notification, scheduler, legacy write, or secondary transaction.

### `listDraftInventory` query

Arguments: `requestId`, selected `category`, and a bounded cursor token/limit contract capped at 12 cards.

- Initiator-only and draft-only.
- Map the Quality Time category to its one exact supported legacy category and read `planIdeas` through `by_couple_and_category` in a bounded page; do not scan or use `.filter()`/unbounded `.collect()`.
- Exclude already-decided option IDs using the initiator's category decisions read at the 65-row overflow cap.
- Return neutral allowlisted card display fields and an opaque pagination result. Never return `createdByUserId`, `sourceCreatedByUserId`, source attribution, couple/user IDs, legacy swipe/match state, or another category.

If the existing index cannot support stable bounded pagination without changing legacy schema, use Convex pagination on `by_couple_and_category`; do not add or rewrite a legacy-table index in this slice.

### `recordDecision` mutation

Arguments: `requestId`, `expectedVersion`, `planIdeaId`, and `decision`.

Initiator path:

- Require `draft`, a selected exact-mapped category, current version, and the 64-per-category cap.
- Validate the authoritative idea belongs to the request couple and create exactly one immutable option snapshot plus one private decision in the same transaction.
- Reject already-seen ideas, duplicate/ambiguous option/decision evidence, and wrong/unknown categories. Increment request version once.

Responder path:

- Require `responding`, a responder-selected category, current version, and an existing option that is in the initiator's sent accepted shortlist.
- Never accept arbitrary inventory outside that shortlist. Insert one responder decision and increment version in the same transaction.
- On mutual accept, validate through 07-01 policy and insert the category outcome in that same transaction. If an outcome already exists, the category is stopped and any further decision fails closed.
- After each responder decision, boundedly derive whether every responder-selected category is resolved by either one mutual outcome or complete consumption of its 3–5-card shortlist. If so, mark the request `completed`; exhausted categories project only neutral `no_match`. A category with a mutual outcome never reveals remaining decisions.

All stale versions fail before writes, including superficially equivalent retries. Duplicate rows are not treated as idempotent success because ambiguity could hide a conflicting private decision.

### `sendRequest` mutation

Arguments: `requestId`, `expectedVersion` only.

- Initiator-only and draft-only.
- In **one Convex mutation transaction**, boundedly load every selected category's initiator decisions/options, reject overflow/duplicates/mismatches, and pass the exact evidence to 07-01 shortlist readiness.
- Transition to `sent`, set `sentAt`, and increment version only when every selected category has 3–5 unique initiator accepts. Two accepts is ordinary not-ready; six accepts, malformed evidence, duplicate IDs/categories, cross-category options, or ambiguous rows fail closed with no partial write.
- Persist no copied shortlist array and perform no follow-up mutation/action. The committed decisions are the authoritative send snapshot and cannot change after send.
- Do not notify or schedule anything. A later notification slice may react only to committed `sent` state under separate approval.

### `beginResponse` mutation

Arguments: `requestId`, `expectedVersion`, and `categories` only.

- Responder-only and sent-only.
- Require a non-empty unique subset of request categories; persist it once as `responderCategories`, transition to `responding`, and increment version.
- The initiator projection must not reveal responder category choices. Duplicate/stale calls fail closed.

### `getRequest` query

Argument: `requestId` only.

- A draft is visible only to its initiator; the responder receives the same not-found/unauthorized disposition used for foreign/cross-couple request IDs.
- Initiator draft projection: own timing/categories/version and own coarse counts only; never expose stored authorship.
- Initiator sent/responding projection: timing/categories/status/version plus coarse waiting/resolved state only; no responder categories, cards, decisions, passes, accepts, order, or exhaustion reason.
- Responder sent projection: neutral request timing/categories/status/version; no cards until `beginResponse` commits.
- Responder responding projection: own selected categories and only the neutral 3–5-card initiator-accepted shortlist for each; omit initiator decision fields/order and omit all non-shortlisted or hidden-category options.
- Completed projection for either partner: only timing, terminal neutral category status, and allowlisted option snapshot for each mutual outcome. No unmatched accepts, rejected IDs, decision rows/order, or `createdByUserId`/`sourceCreatedByUserId` is ever returned. Authorship remains hidden even at mutual outcome in this slice.
- Canceled/expired/no-match projections are neutral. No partner-private reason/evidence is returned.

### `cancelRequest` mutation

Arguments: `requestId`, `expectedVersion` only.

- Either current request participant may cancel a draft/sent/responding request; derive actor server-side, set `canceledAt`, and increment version.
- It creates/deletes no decisions or outcomes and writes no legacy state. Completed/canceled/expired and stale requests fail closed.

Expiration is schema/projection-ready but there is no scheduler, cron, action, deployment, or bulk expiry worker in this slice. Queries must derive an effective `expired` projection when server time is beyond `expiresAt` without exposing stale private state. A state-changing mutation that encounters an otherwise valid overdue request must atomically mark it `expired`, increment its version, and return an explicit terminal `expired` disposition rather than throw (a thrown Convex mutation would roll back the expiry write); malformed, ambiguous, unauthorized, or stale-version evidence still throws before writes. Any broader expiry reconciler is a later plan.

## Privacy and bounded-read invariants

- No responder can discover a draft through success/error shape, list API, projection, or card API.
- No pre-mutual projection contains creator/authorship, partner decision value, rejected option ID, hidden-category card/decision, or decision order/timestamp.
- An initiator cannot inspect responder categories or choices while waiting.
- Only an exact same-request, same-category, same-option double accept creates/reveals an outcome.
- Every collection read is indexed and bounded. Do not use `.filter()`, unbounded `.collect()`, or scan legacy tables. Direct `db.get` calls must still validate request/couple/category ownership.
- `.first()` must not silently choose among rows expected to be unique. Use `.unique()` where exact schema uniqueness is safe or bounded duplicate detection where fail-closed handling is required.
- Request `expectedVersion` must be a finite nonnegative integer and exactly equal the persisted version. Every successful state-changing mutation increments once; stale/future/malformed versions write nothing.
- Validation or ambiguity failure writes nothing because each mutation is a single Convex transaction. Never split send readiness, responder match creation, or terminal completion into actions/follow-up mutations.
