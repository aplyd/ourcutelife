# Phase 6 Slice 06-02 — Immutable Prompt Assignment and Exact-Once Completion Plan

**Goal:** Freeze one safe reusable daily prompt per authoritative couple-day lifecycle and count a couple's completion exactly once, without adding an AI/model call or weakening private-until-both-submit behavior.

**Business outcome:** Both partners see and answer the same historical question even if the code-owned fallback bank changes, while completed prompts gain reusable ranking evidence without exposing either partner's answer or identity.

## Scope

### Additive schema

Modify `convex/schema.ts` only additively:

- Add `dailyPrompts` with:
  - `text`
  - `normalizedFingerprint`
  - `principle`
  - `category`
  - `source: "seed" | "ai"`
  - `safetyStatus: "pending" | "approved" | "rejected"`
  - optional `model`, `generationPromptVersion`, and `generatedAt` provenance reserved for the later AI slice
  - `completionCount`
  - `createdAt`, `updatedAt`
- Index `dailyPrompts` by the full fields used for exact fingerprint lookup and bounded approved-candidate ranking. Use index names containing every indexed field, for example:
  - `by_normalized_fingerprint`
  - `by_safety_status_and_completion_count_and_created_at`
- Add optional `promptId: v.id("dailyPrompts")` to `dailyPromptLifecycles` for additive rollout compatibility.
- Add `dailyPromptCompletions` with:
  - `lifecycleId`
  - `coupleId`
  - `promptDate`
  - `promptId`
  - `completedAt`, `createdAt`
- Index completions as:
  - `by_couple_id_and_prompt_date`
  - `by_lifecycle_id`
  - `by_prompt_id_and_completed_at`

Do not remove or rewrite `promptResponses.prompt`; it remains compatibility/history text during this slice.

### Reusable seed inventory

Create a small prompt-library module that owns the existing six fallback questions as stable seed definitions.

Each seed must have:

- stable normalized text and fingerprint derivation
- explicit principle/category metadata
- `source: "seed"`
- `safetyStatus: "approved"`
- no Moment text, Moment tags, answers, user IDs, couple IDs, or generated personalization

The implementation may ensure the six rows transactionally when assigning a prompt, but must be bounded to the six known definitions and converge by exact fingerprint. This repository run must not execute a live backfill or deployment.

### Immutable lifecycle assignment

Extend the existing lifecycle reconciliation transaction in `convex/dailyPromptLifecycles.ts`:

1. For a newly created lifecycle, ensure bounded approved fallback inventory and choose one candidate deterministically from indexed, bounded results.
2. Persist `promptId` in the initial lifecycle insert. The reference is immutable after first assignment.
3. For an existing legacy lifecycle without `promptId`, assign exactly once in the same reconciliation mutation, then return the lifecycle normally.
4. For an existing lifecycle with `promptId`, validate that the referenced prompt exists and is approved; never replace it because ranking, bank order, metadata, or code changes.
5. Fail closed on duplicate fingerprints, duplicate lifecycle rows, a missing referenced prompt, a rejected/pending referenced prompt, or incompatible assignment state.

Candidate choice in this slice may be deterministic and simple. It must use approved rows only, perform indexed bounded reads, and exclude a bounded recent assignment history for the same couple where inventory permits. Full rank/recency/diversity policy belongs to a later slice.

### Canonical reads and answer writes

Update the daily-prompt path so persisted assignment is authoritative:

- `dailyPromptLifecycles.getTodayState` returns the assigned prompt text/metadata when `promptId` exists.
- `prompts.today` reads the assigned prompt and uses its principle; it must not derive the displayed question from Moment tags.
- Weekly-game and Tiny Quiz behavior stay outside this slice. They may retain their current deterministic behavior, but their metadata must not be presented as the assigned daily prompt's principle.
- `prompts.answer` ensures/requires the lifecycle assignment and derives compatibility `promptResponses.prompt` from the referenced `dailyPrompts` row, never from client text or the mutable in-code bank.
- The existing client compatibility `prompt` argument remains ignored.
- Existing answer visibility remains unchanged: a partner response is returned only after both partners have submitted.

A legacy lifecycle may temporarily render the deterministic fallback while the existing client reconciliation is in flight, but answer persistence must not proceed until the mutation has frozen `promptId`; the post-reconciliation query must converge on the persisted assignment.

### Exact-once private completion

Within the same `prompts.answer` mutation transaction, after the response insert/update:

1. Load both expected couple-member response rows using existing indexed, bounded lookups.
2. Validate exact two-member ownership and reject duplicate/mismatched rows.
3. If both non-empty responses exist, query `dailyPromptCompletions` by `(coupleId, promptDate)` with a bounded duplicate check.
4. If no completion exists, insert one completion row and increment the referenced prompt's `completionCount` once.
5. If the exact completion already exists, return normally without changing the count.
6. If a completion points at a different lifecycle or prompt, fail closed.

The completion row must not contain answer text, user IDs, Moment data/tags, notification state, or partner identity metadata.

### GREEN 1 — Additive inventory and assignment

### RED 2 — Canonical prompt read/write

Add focused tests proving:

- both authenticated partners receive the same persisted question and principle
- Moment tags cannot alter the assigned daily question
- changing the fallback bank after assignment cannot alter `today` or saved compatibility prompt text
- forged client prompt text remains ignored
- a missing/ambiguous assignment cannot save an answer
- partner answer reveal remains hidden until both submit

### GREEN 2 — Read and answer integration

Route `getTodayState`, `prompts.today`, and `prompts.answer` through the persisted prompt reference without broadening game/quiz behavior.

### RED 3 — Exact-once completion

Add focused tests proving:

- the first answer creates no completion and no rank increment
- the second distinct partner answer creates one completion and increments once
- retries, edits by either partner, and concurrent/replayed second-answer attempts do not increment again
- duplicate or mismatched completion state fails closed
- separate couples completing the same prompt create separate private rows and increment the aggregate once per couple
- completion/ranking records contain no answer, user, Moment, or tag fields
- no query exposes another couple's completion row or answer

### GREEN 3 — Transactional completion boundary

Implement completion creation and count increment inside `prompts.answer`'s existing transaction. Do not schedule a follow-up mutation and do not split the rank update into a second transaction.

## Definition of done

This slice is complete only when one approved reusable prompt is immutable per lifecycle; both partners read and save against that reference; exactly one private completion and one aggregate increment occur after both answers; edits/retries/concurrency cannot inflate rank; no answer, user, Moment, or tag data enters reusable/completion records; existing Phase 5 tests remain green; the mobile prompt sheet is walkthrough-verified; review finds no unresolved Medium-or-higher issue; and no deployment, live migration, provider call, credential change, real notification, push, or unrelated worktree rewrite occurred.
