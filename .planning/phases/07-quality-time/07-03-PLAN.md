## Outcome

Add the first additive Quality Time mobile path so one partner can start a request, choose `now` or a future time, select one or more accepted categories, privately pass/accept neutral cards until every selected category has 3–5 accepts, and send the completed request. After send, the initiator sees only a neutral waiting state.

This slice is deliberately initiator-only. It does not add the responder category/swipe/outcome UI, request notifications, inbox/history discovery, legacy cutover, deployment, migration, or live-data verification.

## Route and interaction contract

### `/plans`

Add one clearly separated Quality Time card or primary action near the top of Plans:

- Visible language: `Quality Time` and a concise promise about privately finding what both partners want now.
- Named button: `Start Quality Time`.
- Route: `/plans/quality-time/new`.
- Do not rename, hide, reorder, or change behavior of the legacy surprise, match history, swipe, Our Dates, or Explore Dates controls in this slice.

### `/plans/quality-time/new`

The initiator composer must:

- expose `Back to Plans` as a named button;
- expose `Now` and `Plan for later` as named buttons with exactly one selected state;
- for `Plan for later`, expose one named future date/time field and reject empty, invalid, non-finite, or non-future values before mutation;
- expose all locked categories as named toggle buttons with selected state:
  - `Eat`
  - `Drink`
  - `Explore/Adventure`
  - `Entertainment`
  - `Romance`
- require at least one selected category;
- expose `Choose private options` as a button whose disabled/busy state mirrors the exact local validity/submission gate;
- call only `qualityTime:createDraft` with the accepted timing discriminated union and selected category values;
- navigate on success to `/plans/quality-time/{requestId}`;
- retain the form and show an honest inline error on failure;
- never show partner identity, creator/authorship, notification promises, or legacy `date` terminology.

### `/plans/quality-time/[requestId]`

The initiator request route must:

1. Query `qualityTime:getRequest` and render only the approved initiator projection.
2. For a draft, show the selected categories, timing, and per-category progress from `shortlistCounts`; do not infer progress from hidden local-only arrays.
3. Query `qualityTime:listDraftInventory` for only the active selected category, with `numItems <= 12` and an opaque cursor.
4. Render one neutral card at a time with allowlisted title, description, kind, cost/duration/tags, and optional image/address only.
5. Expose `Pass {card title}` and `Accept {card title}` as named buttons with shared disabled/busy state while one decision is pending.
6. Call `qualityTime:recordDecision` with `planIdeaId`, the latest server-projected `expectedVersion`, and `pass`/`accept`; never accept or transmit a user/couple/role/category/authorship identity.
7. After each decision, rely on query refresh/server projection for the next card and progress. A stale-version response shows an honest refresh/retry state and must not optimistically claim the decision was saved.
8. Let the initiator switch only among their selected categories through named buttons with selected state.
9. Enable `Send Quality Time request` only when every selected category's server-projected accepted count is 3–5. Its accessibility disabled/busy state must mirror the exact gate.
10. On send, call only `qualityTime:sendRequest` with the latest request version. Never notify from the client.
11. For `sent`, show a neutral `Waiting for your partner` state with no responder categories, choices, sequence, no-match reason, or hidden card evidence.
12. Expose `Cancel Quality Time request` as a named button for draft/sent states, require the existing native confirmation pattern, and call only `qualityTime:cancelRequest` with the latest version after confirmation. Mock verification must not activate the final destructive confirmation.
13. Render canceled/expired states neutrally and provide `Back to Plans`; do not silently recreate or reschedule.
14. Handle empty/insufficient inventory honestly: explain that the category does not yet have enough options and keep Send disabled. Do not pad, duplicate, or auto-accept cards.

## Deterministic mock-auth contract

`mockQualityTimeState.ts` must be independent from legacy mock date-plan state and model exactly one fixture request at a time.

Required fixture inventory:

- at least five neutral cards for each of the five Quality Time categories;
- no creator name, user ID, couple ID, source-authorship label, partner decision, or legacy swipe/match status in any public mock projection;
- stable IDs and ordering so screenshots and tests are repeatable.

Required operations:

- `createDraft`: validate timing/categories, create version 1, initialize zero counts, and return the server-shaped result;
- `getRequest`: return draft counts or neutral sent/canceled state only;
- `listDraftInventory`: return undecided neutral cards for the selected category in the server pagination shape;
- initiator `recordDecision`: require exact current version and undecided card, persist pass/accept privately, and increment once;
- `sendRequest`: require 3–5 accepts in every selected category and increment once into `sent`;
- `cancelRequest`: require exact current version and active initiator-owned state, then increment once into `canceled`;
- every successful operation notifies `useSyncExternalStore` listeners so the visible route refreshes;
- reject stale versions, duplicate decisions, unselected/wrong-category cards, insufficient or overfull send evidence, and terminal-state writes without partial state changes.

The mock may expose a test-only reset function to pure unit tests. It must not add a UI role switcher or pretend to prove the two-partner server lifecycle.
