# 07-05 Plan — In-app responder request discovery

Updated: 2026-08-14
Status: planning-only audit; implementation not started

## Objective

Add exactly one user-visible, additive discovery increment after the independently approved Slice 07-04: a responder can open `/plans`, see each non-expired Quality Time request currently waiting for or being answered by them, and enter the existing `/plans/quality-time/[requestId]/respond` route without being given a request ID or deep link out of band.

This closes the smallest break in the already-implemented two-partner loop: Slice 07-04 proves that a responder with an exact request ID can answer, but the current app never supplies that ID to the responder. This slice is **in-app discovery only**. It does not send notifications, add notification delivery state, add history, reschedule, infer abandonment, reconcile expiry in the background, change cancellation, migrate data, or cut over legacy Plans.

### Why this is the next increment

Responder discovery has the clearest immediate business outcome: the partner can actually reach the completed request flow from the app. It is lower risk than delivery because it is a read-only projection with no provider, scheduler, token, permission, credential, or external side effect. It is lower semantic risk than rescheduling or abandonment because it introduces no new lifecycle transition. It also exercises the additive request indexes and existing responder route without changing private decisions, outcomes, cancellation, or expiry policy.

Exactly one increment is authorized: **active responder request discovery on `/plans`**. Initiator draft/resume discovery, completed history, push delivery, badges on other tabs, and every lifecycle change remain later slices.

## Exact server and client contract

### Schema index

Add only this index to `qualityTimeRequests`:

```ts
.index("by_responder_user_id_and_status_and_updated_at", [
  "responderUserId",
  "status",
  "updatedAt",
])
```

Do not add a discovery table, inbox row, unread/read receipt, delivery attempt, badge counter, or denormalized array.

### `listPendingResponses` query

Add one authenticated public query in `convex/qualityTime.ts`:

```ts
listPendingResponses({});
```

Contract:

1. Derive the authenticated user, exact couple, and exact partner through the same fail-closed membership boundary as existing Quality Time APIs. Accept no user, couple, role, status, cursor, or request ID argument.
2. Read only rows where `responderUserId` is the viewer and status is `sent` or `responding`, using `by_responder_user_id_and_status_and_updated_at` and `.take(11)` for each status. Never scan, use `.filter()`, or use unbounded `.collect()`.
3. Validate every candidate against the current exact pair, persisted version, timing, category, active-state, and shortlist/outcome integrity already required by `getRequest`. A changed pair, malformed row, duplicate/ambiguous evidence, or more than ten combined active candidates fails closed; do not truncate malformed or overflow state into an apparently complete inbox.
4. Treat `now >= expiresAt` as effectively expired and omit that row. The query is read-only: it must not persist expiry, schedule reconciliation, cancel, notify, or mutate any row.
5. Merge `sent` and `responding` candidates, sort deterministically by `updatedAt` descending and request ID as the stable tie-breaker, then return at most ten explicit allowlisted entries.
6. Each entry contains exactly:
   - `requestId`
   - `status: "sent" | "responding"`
   - `version`
   - neutral `timing`
   - `selectedCategories`
7. Return no draft, completed, canceled, expired, initiator-owned, foreign-couple, or changed-membership row. Return no partner identity/name, `responderCategories`, card/option/plan-idea data, shortlist counts, outcome, decision, rejection, authorship/provenance, expiry timestamp, private lifecycle timestamp, or cancellation reason.
8. The query makes no claim that a request was notified, delivered, seen, opened, or acknowledged.

If sharing existing validation helpers would broaden existing projections or alter mutation behavior, extract only private validation logic inside `convex/qualityTime.ts`; do not weaken `getRequest` or return raw documents.

### Typed client projection

Add an exact `QualityTimePendingResponse` type and `listQualityTimePendingResponses` typed query reference to `src/lib/qualityTimeApi.ts`. The client type must mirror only the allowed fields above and must not reuse a broader document-like type.

### Deterministic mock behavior

- Add `listPendingResponses({})` to the existing mock state; it takes no identity/role argument and derives visibility from the fixture's current actor.
- With `seed("mixed")` in its initial `sent` state, the responder receives one neutral `sent` entry and the initiator receives `[]`.
- After the responder begins, the responder receives the same request as `responding`; completion removes it.
- `expired` and `canceled` scenarios return `[]` for both actors. Completed scenarios return `[]`.
- Keep one stable request ID and deterministic ordering. Expose no arbitrary state injection or production role switcher.
- Every returned entry is a fresh explicit projection. Tests assert exact keys and absence of identities, cards, responder category choices, decisions, outcomes, authorship, rejection IDs, timestamps other than projected future `scheduledFor`, and notification claims.

### `/plans` UI

Keep the current Quality Time section and `Start Quality Time` action. Add a responder-only area within that section:

- Query `listQualityTimePendingResponses` independently of legacy Plans data. Its loading state must not block or hide the existing Plans screen or legacy sections.
- If the list is empty, render no waiting-request placeholder and preserve the current Quality Time card copy/action.
- For each `sent` entry, show neutral timing and requested category labels plus a named button `Respond to Quality Time` routing directly to `/plans/quality-time/{requestId}/respond`.
- For each `responding` entry, show the same neutral request summary plus a named button `Continue Quality Time` routing to that same responder route.
- Button order follows the server projection. Each button has `accessibilityRole="button"`; the summary has one stable accessible label that includes status, timing, and requested categories without partner identity.
- Do not show who initiated, whether/how it was delivered, responder-selected categories, progress, remaining card count, accepted/passed choices, matches, no-match reason, expiry timestamp, or authorship.
- A query failure renders a non-specific `Quality Time requests unavailable` message inside this additive section while leaving `Start Quality Time` and every legacy Plans control usable. Do not fall back to cached request cards or manufacture route IDs.
- Do not automatically navigate, mark read, acknowledge delivery, mutate the request, or create a badge outside `/plans`.

## Acceptance criteria

1. As the deterministic responder with one fresh sent fixture request, opening `/plans` exposes a neutral `Respond to Quality Time` button without debugger-supplied route navigation; activating it opens the existing responder route for the exact server-projected request ID.
2. The same request appears as `Continue Quality Time` after response has begun and disappears after completion, cancellation, or effective expiry.
3. The initiator never sees their own sent/responding request in this responder discovery projection or UI.
4. Multiple valid responder requests are deterministically ordered and capped at ten; overflow and malformed evidence fail closed rather than being silently truncated or partially shown.
5. Discovery returns/renders only the exact neutral allowlist. Drafts and every partner-private field remain undiscoverable.
6. Discovery performs no mutation and creates no delivery, notification, read-receipt, scheduler, legacy, prompt, or outcome row.
7. Existing `/plans` content, `Start Quality Time`, all legacy Plans routes, and the approved request/respond/outcome routes retain behavior.
8. Focused backend/unit tests, full regression gates, typecheck, lint, format, whitespace checks, no-edit review, and the Argent contract below pass with recorded evidence.

## Privacy invariants

1. Drafts remain invisible to the responder through list membership, count, error shape, route card, and mock projection.
2. Discovery derives viewer/couple/partner/role server-side and reveals only requests whose snapshotted responder is the authenticated viewer in the current exact pair.
3. Entries expose no identity or authorship, initiator shortlist/decision evidence, responder categories/progress/decisions, cards/options, rejected IDs, outcomes, cancellation actor/reason, or private timestamps.
4. `sent` and `responding` copy is neutral. It must not say or imply that the partner liked a card, that a notification was sent/received, or that silence means rejection or abandonment.
5. Overdue, canceled, and completed rows disappear without explaining why or who acted. Existing exact-ID terminal routes remain neutral.
6. Cross-couple, changed membership, malformed status/timing/version/categories, duplicate/ambiguous private evidence, and overflow fail closed without leaking which candidate caused failure.
7. No discovery operation writes Quality Time, legacy Plans/Dates/Matches, prompt lifecycle, notification device, delivery-attempt, or provider state.

## Coexistence and rollback constraints

- **Additive coexistence:** keep `/plans`, `Start Quality Time`, all legacy sections/routes, and all approved Quality Time routes/APIs unchanged. Discovery is an additional read projection and an additional card group only.
- **No cutover:** do not remove, rename, reorder, or demote Surprise, Match history, Swipe plan items, Our Dates, Explore Dates, Matched Items, `/plans/new`, `/plans/random`, `/plans/history`, or `/plans/match/[category]`.
- **No dual-write or migration:** do not create inbox/read-receipt rows, backfill requests, reinterpret legacy state, or import history. The index is additive and existing rows need no data rewrite.
- **No delivery coupling:** this query/UI must work without notification permission, device readiness, tokens, scheduler jobs, providers, or credentials. A later notification slice may deep-link to the same existing route but must not be inferred from discovery approval.
- **Rollback:** remove the Plans discovery rendering, typed query reference, mock query dispatch/projection, public query/tests, and additive index. Leave all Quality Time rows, existing routes/APIs, notification infrastructure, and legacy data untouched. `/plans` returns to its approved 07-04 state with `Start Quality Time` as the only Quality Time entry.
